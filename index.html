先闭环 逐步加深 拒绝一次做完

先让一个 Agent 用好一批私人数据，再逐步建设完整平台

原 PRD 适合作为最终能力地图，但不适合作为首个版本的开发清单。 新计划以“单用户、网页端、NAS 数据、Agent 可检索并生成有来源的产物”为 MVP， 把多模态理解、外部操作、手机 App、共同记忆、多用户和完整治理分阶段加入。

MVP 唯一目标 将 NAS 中的私人文件登记为可追溯数据，让用户可以浏览和搜索， 让一个持有 Token 的 Agent 可以在权限范围内检索、读取并生成带来源引用的新报告， 且每次操作都有事件记录。
Split Rules

四条复杂度控制原则

这些原则用于阻止完整 PRD 再次整体进入首版。

01 · 先数据后动作

先证明 Agent 找得到

没有稳定的数据登记、检索、引用和权限过滤前，不接浏览器、邮件及其他外部动作。

02 · 先网页后 App

先稳定后端契约

MVP 使用桌面网页。Flutter App 在上传、对象、权限和事件 API 稳定后开始。

03 · 先单用户后多用户

保留 user_id，不做管理体系

数据模型从第一天带用户字段，但 MVP 只服务一个实际用户，不建设跨用户管理。

04 · 事件从第一天开始

先记录，不先做复杂恢复

MVP 记录谁做了什么及结果；检查点、重放、补偿和多 Agent 交接后续增加。

MVP Scope

MVP 只做一个最小真实闭环

预计 3–4 周，不含前置技术验证。时间为单人配合 AI 开发的规划值，不是固定承诺。

必须完成

  • 扫描并登记 `/volume1/agent-first-data` 中的现有文件。
  • 网页上传、列表、详情、下载、基础预览和软删除恢复。
  • 稳定对象 ID、内容哈希、来源、类型、大小和时间元数据。
  • PDF/纯文本正文提取；其他媒体先登记基础元数据。
  • Voyage AI Embedding，MongoDB 元数据过滤与向量搜索。
  • 一个用户、一个管理员、一个 Agent Token。
  • Agent 搜索、读取和创建派生报告的 API。
  • 上传、读取、搜索、生成、删除和恢复的事件记录。

明确不做

  • 不做 Flutter 或原生手机 App。
  • 不做多用户后台和跨用户访问。
  • 不做浏览器、邮件、记账等外部操作。
  • 不做图片视觉理解、音频转录和视频关键帧理解。
  • 不做 Skill 商店、复杂记忆晋升和多 Agent 协作。
  • 不做完整 Task/Run/Checkpoint 恢复引擎。
  • 不做 S3 实际部署，只保留存储适配器接口。
  • 不做永久物理清除，只做可恢复软删除。
1 · 登记扫描 NAS 文件或网页上传，生成稳定对象 ID。
2 · 提取保存元数据，提取 PDF 与文本内容。
3 · 索引生成向量，记录模型、输入哈希和状态。
4 · 检索用户或 Agent 根据问题找到相关数据。
5 · 生成Agent 创建带对象引用的派生报告。
6 · 留痕所有访问和变化进入追加式事件记录。
MVP 验收门槛 当前 20 个样例文件全部登记且 Raw 不被改写；PDF 可检索；Agent 能生成一份带来源对象 ID 的报告； 所有 Agent API 调用可追踪；软删除后不再被搜索且可以恢复。
Roadmap

从 MVP 到最终功能的六次迭代

每个版本只增加一种主要复杂度，不同时引入数据、终端、权限和运行时四类变化。

阶段 0技术验证3–5 个工作日

证明关键依赖可用

  • NAS 目录只读扫描与测试目录写入
  • MongoDB 数据模型和基础索引
  • Voyage AI 调用与费用记录
  • 文件哈希、对象 ID 与存储适配器
  • 本地开发和 NAS 容器运行验证
进入 MVP 的条件

20 个样例文件可稳定扫描；重复扫描不产生重复对象；任意对象可由逻辑 ID 定位回 NAS 文件。

MVP数据可被 Agent 使用3–4 周

完成最小真实闭环

  • 网页数据管理
  • PDF/文本提取和向量检索
  • Agent Token 与三项核心 API
  • 派生报告和来源引用
  • 基础事件记录与软删除
版本价值

首次证明 Agent 可以在不直接遍历 NAS 的情况下，安全地发现、读取和引用私人数据。

V0.2多模态上下文3–4 周

让更多文件真正可搜索

  • 图片 EXIF、缩略图、OCR 和视觉描述
  • 音频转录、时间片段和摘要
  • 视频关键帧、音轨转录和时间定位
  • 全文 + 向量 + 元数据混合检索
  • Rerank、Chunk 和索引生命周期
进入下一阶段的条件

四种媒体均能返回可引用片段；索引失败可见、可重试；源文件变化能触发重新处理。

V0.3Agent 执行4–5 周

从“检索”升级为“完成任务”

  • Task、Run、Step 和最小检查点
  • Agent 修改草稿、创建正式产物
  • 动作风险等级与逐次审批
  • 浏览器能力优先接入，邮件随后接入
  • 重试、取消、超时和外部动作收据
进入下一阶段的条件

一个中断任务可继续；外部动作均能看到原因、授权、输入、结果和失败状态。

V0.4手机采集与记忆4–6 周

建立日常使用入口

  • Flutter App 拍照、选择文件、分享导入
  • 后台上传队列、断点续传和失败重试
  • 手机浏览、搜索、软删除和审批
  • 任务摘要、经验候选和用户纠正
  • 基础 Tool/Skill 注册、版本和测试状态
进入下一阶段的条件

手机采集数据可在 Agent 检索中出现；换一个 Agent 后能读取任务摘要和已确认经验。

V1.0可正式使用4–6 周

补齐生产治理

  • 网页多用户管理，App 单用户登录
  • 细粒度 Token、临时授权和跨用户原因
  • 回收站、待清除、永久清除和备份过期
  • 管理员“仅系统管理/临时授权”模式
  • S3 适配、备份恢复、监控和安全加固
正式使用条件

权限越界测试全部拒绝；备份恢复演练通过；删除链路可解释；NAS 故障不会造成元数据与 Raw 对象关系丢失。

V2+Agent 操作系统按真实需求演进

只在使用量证明必要后建设

  • 多 Agent 协作、交接和长期运行
  • 完整检查点、事件重放和补偿事务
  • 时间视图与历史上下文复现
  • 反馈评估、经验晋升和 Skill 回归测试
  • 记账及更多第三方权限域
启动依据

不是因为架构“应该有”，而是已有任务量、失败模式或协作需求无法由 V1 解决。

MVP Architecture

MVP 使用模块化单体，不拆微服务

部署简单，但代码边界清楚，后续版本可以在不替换数据模型的情况下扩展。

Web

上传、浏览、搜索、详情、删除恢复和 Agent 产物查看。

应用后端

单一 API，内部按数据、检索、Agent、权限、事件模块分层。

NAS Adapter

Raw 文件只通过存储适配器访问，不把绝对路径暴露给 Agent。

MongoDB

对象、元数据、任务、事件和向量索引使用同一数据库起步。

处理 Worker

文件提取、Embedding 和重试；MVP 不引入 Kafka 或 Kubernetes。

从第一天保留，但暂不实现完整功能 所有对象包含 user_id、storage_provider、version、source 和 sensitivity； 所有事件包含 actor、action、target、purpose、status 和 correlation_id。 这些字段用于保证后续多用户、S3、权限和任务恢复无需重建基础数据。
Delivery Gates

每次迭代的交付规则

避免“功能做了很多，但没有一个版本真正可用”。

范围冻结

迭代开始后，新想法进入候选池。除非阻塞当前闭环，不临时加入开发范围。

证据验收

每个版本必须用真实 NAS 样例、真实 Agent Token 和失败场景演示，不能只看页面。

人工激活

版本通过验收后由用户决定是否进入下一阶段；未通过则修复，不用新功能掩盖问题。

建议立即锁定的第一项工作 先完成阶段 0，不直接进入完整 MVP。阶段 0 的输出应是一份可重复运行的技术验证报告， 明确 NAS、MongoDB、Voyage AI、对象 ID 和部署方式是否真实可行。
